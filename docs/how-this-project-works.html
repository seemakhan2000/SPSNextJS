How this site is built

A walkthrough of the real files in this repo: homepage sections, navbar, CSS/JS, and how product pages share components. Open the matching files in Cursor while you read.

How to use this file: keep this page open, and in the editor search for the file names in src/. Everything below is from this project, not generic Next.js theory.

1. What you are looking at

This is a Next.js App Router site. Pages live in src/app/. Shared UI lives in src/components/. Content/data lives in src/lib/. Images, old theme CSS, and vendor JS live in public/assets/.

@/ is a shortcut for src/. So import Header from "@/components/layout/Header" means src/components/layout/Header.jsx. That alias is set in tsconfig.json.

Server components (default)

Most .jsx files in this repo have no "use client". Next.js renders them on the server into HTML. They can import data from src/lib and pass it as props.

Client components

Files that start with "use client" run in the browser. Examples: SiteBehaviors.jsx, VerticalsNav.jsx, contact form. They handle clicks, sliders, and modals.

3. The page shell (every URL)

When you open any URL, Next.js nests layouts. Think of a sandwich:

src/app/layout.jsx Root layout. Loads CSS, fonts, JSON-LD. Renders Header then {children} then Footer.
Optional nested layout Example: src/app/products/layout.jsx adds the appointment modal and SiteBehaviors only on product URLs.
The page file Homepage is src/app/page.jsx. Products listing is src/app/products/page.jsx.
// src/app/layout.jsx — simplified
<html>
  <head>
    <link rel="stylesheet" href="/assets/css/style.css" />
    <link rel="stylesheet" href="/assets/css/navbar-v2.css" />
    ...
  </head>
  <body>
    <Header />      ← navbar lives here, so it is on every page
    {children}     ← the actual page content
    <Footer />
  </body>
</html>

That is why you do not import the navbar inside homepage sections. The homepage only fills {children}.

Hero in more detail

Hero.jsx is still a server component. It outputs HTML that Swiper expects: .swiper.heroSwiper > .swiper-wrapper > .swiper-slide. Inside a slide you will see helper components defined in the same file: HeroCopy, HeroActions, HeroHighlights. Those are not routes — they are just small pieces of the same file.

Desktop uses a <video>. Mobile uses a still image /assets/images/spsimg/banner/bg-v4.avif (also preloaded in the root layout).

Buttons with data-open-appointment do not navigate. SiteBehaviors listens for that attribute and opens the modal.

Mental model: homepage components are mostly HTML + Tailwind classes copied from the old PHP theme. Interactivity is not inside those files. It is attached later by SiteBehaviors looking up CSS class names in the DOM.

5. How the navbar is linked

1. Root layout mounts Header src/app/layout.jsx always renders <Header /> above the page.
2. Header is the chrome src/components/layout/Header.jsx — logo, internship link, info drawer, hamburger. It imports Navigation.
3. Navigation is the menu links src/components/layout/Navigation.jsx — Home, Product mega menu, Services, Verticals, etc.
4. CSS paints it public/assets/css/navbar-v2.css styles .navbar-v2, dropdowns, mega menus.
5. JS opens dropdowns / mobile menu public/assets/js/navbar-v2.js is loaded by SiteBehaviors. It watches data-nv2-dropdown, #navbarV2Nav, the overlay, the drawer.

Two kinds of links in the navbar

You seeCodeWhy
Internal pages (Home, Products, BMS) <Link href="/products/bms"> from next/link Client-side navigation. No full page reload. Prefetches the page.
External sites (Azalio, Fabrico) <a href="https://..." target="_blank"> Leaves this app. Regular browser link.
Not built yet href="/coming-soon" Placeholder route src/app/coming-soon/page.jsx.

Product mega menu examples from Navigation.jsx:

<Link href="/products">Product</Link>
<Link href="/products">View All Products</Link>
<Link href="/products/bms">BMS</Link>
<Link href="/products/automation">Automation</Link>

Those paths are not invented in the navbar. They match folder names under src/app/products/ plus slugs from src/features/products/data/products.js.

Verticals mega menu is data-driven: verticalMegaMenu is imported from src/lib/verticals.js and mapped to <Link>s. Change the data file, the menu updates.

Important: SiteBehaviors (which loads navbar-v2.js) is not in the root layout. It is added on the homepage and on nested layouts (products, services, verticals, contact, VITA). If a future page forgets to include it, the hamburger / mega menu JS may not boot on that route.

Because they are in public/, the browser requests them as static files. Next.js does not hash those filenames.

7. JS — how behavior works

File: src/components/home/SiteBehaviors.jsx ("use client"). It returns null — you never see it. On mount it:

  1. Wires click handlers written in React: appointment modal, read-more, offcanvas, box-hover, tabs, filters.
  2. Dynamically injects <script src="/assets/vendor/swiper/swiper-bundle.min.js">.
  3. Starts Swipers: .heroSwiper, homepage carousels, customer logos, service card swipers.
  4. Loads /assets/js/navbar-v2.js for the header.
  5. Later (idle) loads leftover theme scripts: custom.js, dz.ajax.js.
// the magic hook for the appointment popup
document click → closest("[data-open-appointment]")
             → add class "active" on #appointmentModal
             → lock body scroll

So a product CTA does not need its own React state. Put data-open-appointment on a button anywhere, as long as that page also rendered AppointmentModal + SiteBehaviors.

Tabs: SiteBehaviors.initTabs() only targets .custom-tab (homepage / services markup). React-controlled tabs such as vertical service tabs must not use that class, or both systems fight over clicks.

8. Products — data, routes, components

Products are not separate HTML files per item. There are three route templates and one big data file.

The data file

src/features/products/data/products.js holds:

  • productFamilies — SPS / IBM / Other (used on /products)
  • categories — Automation, Security, BMS, …
  • products — individual items under a category
  • helpers: categoryPath("automation") → /products/automation
  • productPath("automation", "watsonx-orchestrate") → /products/automation/watsonx-orchestrate
  • getCategory, getProduct, getProductsByCategory

The three URLs

URLFileWhat it renders
/products src/app/products/page.jsx PageBanner + FamilyExplorer (families from data)
/products/[category]
e.g. /products/automation		 src/app/products/[category]/page.jsx Looks up category. If layout: "content" (BMS, CSM) → BmsDetail. Else a grid of CategoryProductCard.
/products/[category]/[product] src/app/products/[category]/[product]/page.jsx PageBanner + ProductDetail for one item.

[category] and [product] are dynamic segments. Next.js fills them from the URL, then the page calls getCategory(category). generateStaticParams() prebuilds every known slug. dynamicParams = false means unknown slugs 404.

↓ how a category page decides what to show
const data = getCategory(category)
if (!data) notFound()

if (data.layout === "content") {
  // BMS / CSM — a long custom page, not a card grid
  return <PageBanner ... /> + <BmsDetail category={data} />
}

const items = getProductsByCategory(data.slug)
return items.map(item =>
  <CategoryProductCard product={item} categorySlug={data.slug} />
)

Each card’s “Explore Product” link is:

href = productPath(categorySlug, product.slug)
     = `/products/${categorySlug}/${product.slug}`

That lands on the learn-more page, which passes the same objects into ProductDetail. ProductDetail then composes smaller pieces: images, feature list, AgentTabs, capabilities, video button (popup-youtube class for legacy JS).

Follow one click

Navbar User clicks Product → Automation. Link href="/products/automation".
Route Next matches src/app/products/[category]/page.jsx with category = "automation".
Data getCategory("automation") returns the object from categories in products.js.
UI Banner + map of products whose category field is "automation".
Card User clicks Explore on Watsonx Orchestrate → /products/automation/watsonx-orchestrate.
Detail route [product]/page.jsx calls getProduct("automation", "watsonx-orchestrate") and renders ProductDetail.
Shared chrome Header/Footer still from root layout. Modal + SiteBehaviors from products/layout.jsx.

9. How components are reused

The project avoids copying banners and sliders. One component, many pages, different props.

ComponentBorn forAlso used on
Header / Navigation / FooterSite chromeEvery page via root layout
PageBannerProductsServices, contact, coming-soon, product/service detail
FamilyExplorerProducts listingServices listing (same tabs UI, different families data)
JsonLdProducts SEOServices, verticals, contact
CustomersHomepageEvery vertical page
AppointmentModalHomepageProducts, services, verticals, contact, VITA layouts
SiteBehaviorsHomepage JSSame layouts as the modal
WhyChoose, ProductStats, ProductCtaProduct detailServices listing
VerticalPageAll industry pagesOne template; content comes from verticalPages in verticals.js

Reuse rule in this codebase: put content in src/lib, put layout in a component, put the URL in src/app. The page file should stay small — fetch data, pick a component, pass props.

// services listing reuses product UI

11. Practice path (do this in order)

  1. Open src/app/layout.jsx and src/components/layout/Header.jsx. Confirm Header wraps every page.
  2. Open src/app/page.jsx. Click each import and scroll the matching homepage section in the browser at http://localhost:3000.
  3. Search the homepage for data-open-appointment, then read initAppointmentModal in SiteBehaviors.jsx.
  4. Click Product in the navbar. Trace href="/products" → src/app/products/page.jsx → FamilyExplorer → categoryPath(slug).
  5. Open a category, then a product. Watch the URL segments match [category] and [product].
  6. Change a product summary in src/features/products/data/products.js and refresh — the card text should change. That proves pages are data-driven.
  7. Open src/app/verticals/[family]/[vertical]/page.jsx. See how one file serves Government, Education, Telcos, etc.
One sentence summary: layouts wrap the chrome, page files only assemble sections, src/lib owns the content and URLs, shared components take props, and SiteBehaviors plus files in public/assets add the old theme’s CSS and JavaScript on top.
